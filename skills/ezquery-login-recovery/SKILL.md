# EZQuery 登录恢复

帮助用户在当前电脑上恢复 EZQuery 认证。这个 Skill 只处理认证和本机回调，不执行游戏查询或修改项目代码。

## 适用边界

- 适用于 EZQuery 的 `local` 或 `online` 环境；默认沿用客户端配置的环境，用户明确说“线上”时使用 `online`。
- 用户必须亲自完成扫码、密码输入或其他二次认证；不要索要、复制或在聊天中展示 token、Cookie、验证码或密码。
- 不要为了“清缓存”而盲目清空全部浏览器数据。优先重建一次登录会话；只有用户明确要求时才处理指定站点的 Cookie/缓存。
- 如果目标远程登录服务、账号或浏览器不明确，先说明当前使用的环境和回调地址。

## 工作流程

### 1. 先确认凭证状态

找到当前使用的 `ezquery_client.py`（通常位于 `ezquery-client/scripts/`），执行：

```bash
python3 <ezquery-client>/scripts/ezquery_client.py status
```

如果目标环境的凭证仍然有效，直接告知用户无需重新登录；不要使用 `--force` 覆盖有效会话。

### 2. 判断是否需要重建本机回调

出现以下情况时，使用客户端自带的回调监听重新发起登录：

- 认证页面提示请求失败或旧页面反复失败；
- 两台电脑/多个浏览器同时扫码后，旧页面失效；
- 认证成功后跳转到 `localhost:<port>/callback`，但提示 `ERR_CONNECTION_REFUSED`；
- 客户端状态显示凭证无效或已过期。

启动命令（以目标环境替换 `<env>`）：

```bash
python3 <ezquery-client>/scripts/ezquery_client.py login --env <env> --force
```

这个命令会在本机监听配置中的回调端口并打印认证 URL。不要手工拼接回调 URL，也不要在没有监听器时直接打开旧的 localhost 回调地址。

### 3. 在浏览器中完成认证

使用浏览器控制能力打开客户端打印的认证 URL：

1. 如果页面已识别出用户账号，点击“登录”继续；
2. 如果页面显示二维码，把页面交给用户扫码；
3. 用户完成认证后等待页面跳转回本机回调。

避免同时打开多个新的登录页或在另一台电脑重复扫码，以免新的会话使旧会话失效。

### 4. 验证成功

同时检查两处：

- 浏览器回调页显示 `Login Success!` 或等价的成功提示；
- 登录命令输出 `登录成功`，随后再次执行 `status`，确认目标环境 `valid: true`。

向用户只报告账号显示名、环境和有效期，不回显完整 token 或回调 URL 中的敏感参数。

## 常见故障处理

| 现象 | 处理 |
| --- | --- |
| `localhost:<port>` 拒绝连接 | 说明回调监听器未运行或已退出；重新执行第 2 步，保持命令进程运行到回调完成。 |
| 端口被占用 | 不要启动第二个并行登录流程；先确认是否已有登录命令在等待回调，必要时结束旧流程后再重试。 |
| 换浏览器后成功 | 说明旧浏览器会话/站点状态可能已失效；保留新会话，建议后续只用一个浏览器完成认证。 |
| 认证页显示旧账号 | 点击“切换账号”后由用户选择正确账号；不要替用户输入密码或验证码。 |
| 回调成功但客户端仍报失败 | 先检查登录命令是否仍在运行、环境是否一致（`--env` 与 `status`），再重试一次；不要复制回调 URL 中的 token 手工写入配置。 |

## 完成标准

只有在浏览器成功回调、登录命令报告成功、且 `status` 对目标环境显示有效时，才能说“登录已恢复”。否则明确说明卡在哪一步以及需要用户完成的动作。
